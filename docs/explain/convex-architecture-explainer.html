The Ontology Convex Architecture — the reusable core you keep rebuilding

Subject
The layered Convex implementation in ~/dev/sunday/ontology/convex — components, share layer, auth utils, triggers, audit, and durable workflows — read as the extractable core shared by Qualitys, OneOffice, ProjectSaaS, and Agent.io

You asked what makes this implementation sustainable enough to be worth packaging. The short answer: every generic mechanism lives behind a boundary that is mechanically enforced by tests, and every app-specific decision is injected into it from outside. That inversion — kernel components own the machinery, the host injects the policy — is exactly what makes a ~/dev/cvx npm package feasible. This explainer walks the stack layer by layer and ends with a portability map: what lifts out clean, what needs a seam cut, and what stays app-side.

1. The whole stack in one picture

In prose: convex/schema.ts is four lines (defineSchema(domainTables)). convex/convex.config.ts declares typed env vars and mounts five components. Each component gets exactly one root facade file (foundation.ts, approvals.ts, audit.ts, auth.ts, workflows.ts, pool.ts) — the rest of the app never touches components.* directly. That "one facade per component" rule is asserted in convex/__tests__/facades.test.ts.

2. The share layer: zodTable(), one shape → four boundaries

This is the piece you called "the share layer of the main". A single zod shape per entity is masked into every boundary the entity crosses, so the DB validator, the wire validator, and the TypeScript type are literally the same object. From convex/domain/shared/schema.ts:20-103:

const shape = fields(zid)                          // callback gets zid, so id('assignments') works
const storage = z.object(shape).strict()          // what the DB stores
const schema  = storage.extend({ _id: zid(tableName), _creationTime: z.number() })
const insertSchema = z.object(omitShape(shape, options.serverFields ?? [])).strict()
const updateSchema = insertSchema.partial()
const commandInput = z.object(pickShape(shape, options.commandFields ?? [])).strict()
const publicDto    = z.object(pickShape(shape, options.publicFields  ?? [])).strict()
...
table: defineTable(zodToConvex(storage)),         // convex-helpers/server/zod4 bridge
tools: { insert: commandInput,
         update: z.object({ data: commandInput.partial(), id: zid(tableName) }).strict() }

The three masks are the design insight:

  • serverFields — fields the server owns (createdAt, updatedAt): removed from what clients may insert.
  • commandFields — the tiny subset a command is allowed to say (e.g. for assignments only assignedToUserId and snapshot).
  • publicFields — the DTO allowlist. toPublicDto(row) both projects and re-parses, so leaking a private field is a runtime error, not a code-review hope.
Why this is the sustainable move: redaction, input narrowing, and typing are usually three hand-maintained artifacts that drift. Here they are derived, so they cannot drift. There is also zodVariantTable() for discriminated-union tables, and note you have an older parallel copy at src/server/convex/schemas/helper.ts (adds implicit timestamps and a JSON-safe zid for LLM tools) — the package should merge these two into one.

3. utils.ts — auth-aware function constructors

Every public function in the app is built from six constructors, all zCustom* from convex-helpers/server/zod4: authQuery/authMutation/authAction, admin* (adds a role gate), and internal systemMutation/systemAction. The heart is authenticatedUser (convex/utils.ts:185-218):

async function authenticatedUser(ctx: AuthContext) {
  const identity = await ctx.auth.getUserIdentity()
  const user = identity ? await authKit.getAuthUser(ctx) : null
  if (!identity || !user) return App.errors.throw({ code: 'UNAUTHENTICATED' })
  // … extracts organizationId from the WorkOS JWT, maps role,
  // returns a frozen { identity, user, org, role, actor } bundle
}

Three properties worth copying everywhere:

  • The JWT is not the whole truth for actions. Action constructors re-verify membership live against WorkOS (listOrganizationMemberships, statuses ['active']) and fail closed: any WorkOS error throws FORBIDDEN (utils.ts:230-251). Queries and mutations trust the JWT (they're transactional and fast); actions — which touch the outside world — do not.
  • Mutations get triggers.wrapDB(ctx) baked in (utils.ts:150), so trigger enforcement is structurally unavoidable — nobody can "forget" to wrap the db.
  • include() is a fluent index-selection builder (when / matching / otherwise / execute) that hard-caps every read at 100 rows and throws INVALID_REQUEST_BOUNDARY on unbounded queries — a bounded-read discipline instead of hoping nobody writes a full scan.

The WorkOS wiring around it is three small files: auth.ts (new AuthKit<DataModel>(components.workOSAuthKit, …) plus webhook-driven user sync via authKit.events), auth.config.ts (two customJwt providers pointing at WorkOS issuers/JWKS), and http.ts (authKit.registerRoutes on a Hono router). The "Convex user entity" you validate against is the AuthKit component's own user table, read through authKit.getAuthUser(ctx).

4. Triggers — invariants at the database boundary

One app-wide Triggers<DataModel> registry (convex/triggers.ts), domains register into it. The current use is small but exemplary (domain/assignments/triggers.ts):

triggers.register(table, async (_ctx, change) => {
  if (change.operation !== 'insert') {
    throw new Error(`${table} is append-only`)
  }
})  // assignmentVotes and assignmentHistory are evidence tables

Because the wrap happens inside the mutation constructors, "append-only evidence table" is an invariant of the runtime, not a convention. This is the pattern for anything that must hold no matter which mutation writes: denormalized counters, cascading cleanups, immutability.

5. The foundation component — a kernel that owns nothing

The most unusual and most portable piece. components/foundation is a Convex component with zero tables (defineSchema({}), enforced by test) and one trivial function (status). Its value is entirely in the client-side classes it ships:

  • Command<Context, Registry> — a registry of operations, each { command, result } as zod parseables. exec() parses the input, runs the handler, parses the output too, and rejects unregistered operations with COMMAND_OPERATION_NOT_CONFIGURED. Execution policy is injected: the kernel never decides what "run" means.
  • Query<Context, Defaults> — same idea for reads; the comment in the source says it directly: "Authorization remains an injected host policy."
  • Observability — emits command.execution events with operation, classification, outcome, error code, and clamped duration; gated by a thunk; every emission is wrapped in try/catch because "observability is intentionally behaviorally inert" — telemetry can never break a transaction.
  • executeResultBoundary — returns a handled failure as a value only if the transaction has written nothing yet (checked via ctx.meta.getTransactionMetrics()); otherwise it rethrows so Convex rolls back. Typed errors without ever committing a half-done transaction.

The host binds it once (convex/foundation.ts):

export const { Command, Query, observability } = new Foundation(
  components.foundation,
  { observability: {
      enabled: () => env.COMMAND_OBSERVABILITY_ENABLED === 'true',
      classifyError: App.errors.classifyCommand } },
)

6. ApplicationCommand — where audit stops being optional

The app wraps the kernel once, in domain/shared/command.ts, and this wrapper is what makes every command observable and audited:

return observability.observe({ operation, classification: definition.classification }, async () => {
  const result = await execution.run()
  const audit  = await execution.definition.audit({ command, result }, context)
  if (audit) await writeAuditEntry(context, { ...audit, classification })
  return result
})

The type AuditedOperation makes classification and the audit() factory mandatory fields of every operation definition. You cannot register a command without deciding its audit story — auditing is type-enforced, not opt-in. writeAuditEntry maps the app's shape onto the convex-audit-log component (action, actor, resource, tags, retention category = classification), and the read side is admin-only queries with bounded windowing and tamper-resistant cursors (an FNV-1a fingerprint binds the cursor to its filters, so replayed cursors with different filters are rejected).

Command results are values, not exceptions: a zod discriminated union on ok with denied(code) / success(value) helpers. Combined with executeResultBoundary, a denied command is data the client can render, while an unexpected error still rolls back.

7. Durable workflows — three flavors of the same discipline

PipelinePrimitiveThe discipline it shows
Assignment auto-assign@convex-dev/workflow (own mount) Plan in a retried action, fan out mutations per item, derive a blocked | partial | completed status from step results.
Payment materializationworkflow + @convex-dev/workpool (parallelism 4, backoff retry) Lease tokens guard concurrent runs; loops are bounded (an explicit iteration ceiling that throws rather than spin forever); defineOnComplete routes pool failures back into the workflow.
Approvalsworkflow nested inside the component The component owns its own durable engine — hosts mount nothing extra.

Note the mount naming: the same npm component is mounted twice under different names (assignmentWorkflow, paymentMaterializationWorkflow), each with its own WorkflowManager and pool options — isolation between pipelines comes free from the component model.

8. The approvals component — proof the pattern scales up

components/approvals is a full generic product: declarative approval workflows (decision / branch / mutation / action / notify steps) with quorum, maker-checker, expiry, a compiled-and-frozen descriptor, durable execution, and its own audit trail. What makes it generic:

  • Tenancy is an opaque scopeRef string. The component never resolves identity; the host passes ctx.actor.organizationId. No tenant table needed inside.
  • Callbacks are function handles. Host mutations are stored as opaque strings via createFunctionHandle, so the component calls back into app code it has never imported.
  • A compatibilityKey guards every run-touching call — redefine the workflow shape and old runs refuse to be driven by the new definition.
  • Decisions arrive as workflow events (step.awaitEvent), so a run durably sleeps until a human decides, and evidence is replayed to branch callbacks.

The app-side definition reads like configuration (domain/assignments/approval.ts):

export const assignmentApproval = approvals.define({
  name: 'assignmentApproval',
  steps: [
    approvals.decision('managerDecision', { decisions: ['approved', 'rejected'],
      quorum: { kind: 'count', approvals: 1 }, makerChecker: true,
      expiresAfterMs: ASSIGNMENT_APPROVAL_DURATION_MS }),
    approvals.branch('applyDecision', { approvedStepKey: 'activateAssignment',
      rejectedStepKey: 'releaseAssignment' }),
    approvals.mutation('activateAssignment', { handler: internal.domain.assignments.approval_functions.applyDecision }),
    approvals.mutation('releaseAssignment',  { handler: internal.domain.assignments.approval_functions.applyDecision }),
  ],
})
The copyability test is the crown jewel. components/approvals/__tests__/copyability.test.ts literally cp -r's the component into a temp directory with only node_modules symlinked, generates a minimal host config, and asserts that tsc and convex codegen --dry-run both succeed. Portability isn't a claim — it's a CI assertion. Your npm package should ship this test pattern for every component in it.

9. The enforcement layer — why this stays clean

convex/__tests__/architecture.test.ts loads every production source file as raw text and fails the build on:

  • defineTable/defineSchema outside files named schema.ts; inline z.enum([…]) literals (all vocabularies must come from constants.ts).
  • Deep @server/* imports outside a six-file allowlist; hand-written makeFunctionReference; banned legacy symbols and directories (/bridge/, /migration/, …).
  • foundation.ts importing anything beyond the foundation client; the foundation component importing anything app-shaped at all.
  • The approvals component mentioning @cvx, process.env, WorkOS, Neon, Drizzle, or Redis, and owning any tables beyond its declared two.
This is the real answer to "why is it sustainable". The layering survives because violating it fails CI, not because everyone remembers the rules. When you extract the package, these tests are as much a part of the product as the code: ship a createArchitectureTest(rules) helper so every consuming project gets the same guardrails on day one.

10. Portability map for the ~/dev/cvx package

PiecePortabilityWhat to do
components/foundation Lift as-is. Zero tables, zero app imports, policy injected. Publish as a component; keep the boundary test.
components/approvals Lift as-is. Copyability is already CI-proven. Publish; ship the copyability test as a template.
zodTable / zodVariantTable Lift with a merge. Pure functions over zod + convex-helpers. Unify with the older src/server/convex/schemas/helper.ts variant (timestamps, jsonSafeZid) into one factory with options.
utils.ts constructors Needs one seam. Generic over any DataModel except: AuthKit instance, role mapping, error factory, trigger registry. Export createAuthFunctions({ authKit, mapRole, errors, triggers }) that returns the six constructors + include().
ApplicationCommand + writeAuditEntry Needs one seam. Depends on an AuditLog instance and an observability instance. createApplicationCommand({ observability, writeAudit }); keep AuditedOperation's mandatory-audit typing.
WorkOS wiring (auth.ts, auth.config.ts, http.ts) Templateable. ~30 lines, identical across projects. Ship as a scaffold/init function, not runtime code: the env names and issuer URLs are the only variables.
Audit facade cursor machinery Liftable. Fingerprinted cursors + bounded windows are generic over any AuditLog. Extract; leave the DTO vocabularies app-side.
Workflow/pool tuning, domain registries, DTOs, constants Stays app-side. This is the business. Document the shapes; the package provides the kernels they plug into.

The through-line: this codebase already separated mechanism from policy — the package boundary you want is the boundary the architecture tests already enforce. Extraction is mostly moving code, plus cutting the four injection seams named above (auth deps, error factory, audit writer, observability config) so the mechanisms stop importing your app's singletons and start receiving them.
