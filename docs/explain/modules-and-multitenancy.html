Modules, not entities — and tenancy as a structural feature of cvx-kit

Date
2026-08-13
Input shape

Subject
Evolving cvx-kit's domain layer from entity-per-folder to module segregation, and designing multi-tenancy into the kit — grounded in ~/dev/one-office (multi-tenant Convex ERP) and ~/dev/cvx

The short version. Two upgrades, and they're independent: (1) the unit of the domain layer should be the module (a bounded context owning several related tables), not the entity — your docs currently imply one folder per table, and one-office proves the module shape scales better; (2) tenancy in one-office is not a convention, it's a five-layer structural machine — schema injection, registry-generated row-level security, branded contexts, post-image triggers, and architecture tests — and almost all of it is generic enough to live in cvx-kit as opt-in machinery, with the policy (which identity provider, which claim is the tenant) staying injected, exactly like createAuthFunctions already works.

Part 1 — The domain unit is a module, not a table

Your current docs say domain/<entity>/, one directory per entity, one zodTable per directory. That was true of the app the kit was extracted from — an administration app with few entities. one-office has dozens of tables and does something different: the domain layer is split into bounded contexts, each owning many tables that change together:

The crucial insight from one-office: nothing about the file anatomy changes. Every module still has exactly schema.ts · table.ts · constants.ts · commands.ts · queries.ts · rules.ts · shared.ts · triggers.ts · __tests__/ — its CODE_CONDUCT spells out the identical roles yours does. What changes is the grain: domain/catalog/schema.ts declares several zodTables, and domain/catalog/table.ts exports one merged catalogTables map. The module registry in domain/table.ts then reads like a table of contents for the whole business:

// one-office convex/domain/table.ts — the whole backend in one expression
export const domainTables = { ...sharedTables, ...tenancyTables, ...catalogTables,
  ...inventoryTables, ...purchasingTables, ...salesTables, ...posTables } as const

What defines a module boundary?

Not table count — change cohesion and vocabulary. one-office's CONTEXT.md is a ubiquitous-language glossary (each term with explicit "Avoid:" antonyms), and the modules fall out of it: things named in the same breath (products, prices, unitsOfMeasure) live together as catalog/. A good test for your docs: two tables belong in one module when a single command routinely writes both, or when one's vocabulary is meaningless without the other. If neither is true, separate modules.

The dependency rules that make it safe

Measured from one-office's actual imports, the discipline is precise — and this is what keeps modules from re-blurring into a monolith:

RuleMeaning
Sibling reads: rules.ts / queries.ts only inventory may import catalog/rules (pure predicates) and catalog/queries. It may never import catalog/commands.ts — one module never mutates another's state.
Cross-module writes: application/ A workflow that must atomically touch sales + inventory + invoicing lives in application/postSalesDocument.ts, above both modules. The api/ adapters then import application/* and their own module — never a second module.
domain/shared/ stays generic Cross-cutting kernels (permissions, idempotency, fixed-point math, the command/query policy classes) — never business nouns.
For cvx-kit this is a docs change, not a code change. The kit has no domain/ awareness in code; the entity-per-folder rule lives in conventions.md/architecture.md. Rewrite the grain: domain/<module>/ owning 1..n related tables, the sibling-import rule upgraded from "never" to "rules/queries only, never commands", and a new optional application/ layer for cross-module atomic workflows. A single-context app degenerates gracefully: one module, or a module per entity — the current shape remains a special case of the new rule.

Part 2 — What multi-tenant actually means in one-office

Your origin app was single-org administration: whoever is in the org administers the data, end of story. one-office serves many organizations from one deployment, so every row must answer "whose row is this?" and every read and write must be provably scoped. The design decisions, from its ADR:

  • Tenant = the WorkOS organization id, stored as a plain string field named tenant on every business row. No local orgs/users/memberships tables — WorkOS stays the identity authority, Convex stores one operational-settings record per org. No shadow auth tables to drift.
  • The active tenant is always derived server-side from the JWT's organization claim — never accepted as an argument. Org switching is a frontend/WorkOS concern; when the user switches, the next request carries a different claim.
  • Every index on a tenant table is tenant-prefixed: by_tenant, by_tenant_code, by_tenant_office_archived_at. Reads are impossible to express efficiently without scoping.
  • Tables split into two registries: tenant tables (get all the machinery below) and private/global tables (platform state, cross-tenant uniqueness claims, reconciliation jobs) — deliberately excluded, and therefore the sharpest remaining footgun surface.

Isolation is defense-in-depth, not a convention

The three pieces worth reading in full, because they're the ones cvx-kit should absorb:

// (1) one-office domain/shared/schema.ts — tenancy injected at the schema boundary
export const tenantTable = (tableName, schema, options = {}) => {
  const definition = zodTable(tableName, (id) => ({ ...schema(id),
    tenant: z.string().min(1) }), {...})
  // tenant exists on every row, and can NEVER appear in an update
  const tenantSafeUpdate = definition.updateSchema.omit({ tenant: true })
  return { ...definition, updateSchema: tenantSafeUpdate }
}
// (2) one-office convex/utils.ts — RLS generated mechanically from the registry.
// Nothing per-table to remember: a new tenantTable is isolated the moment
// it's registered, or the exhaustiveness test fails.
export const tenantRules = (tenant: string) =>
  Object.fromEntries(TENANT_TABLE_NAMES.map((tableName) => [tableName, {
    read:   async (_ctx, doc) => doc.tenant === tenant,
    insert: async (_ctx, doc) => doc.tenant === tenant,
    modify: async (_ctx, doc) => doc.tenant === tenant,
  }]))
export const TENANT_RLS_CONFIG = Object.freeze({ defaultPolicy: 'deny' })

// inside tenantMutation: triggers first, then RLS — order matters
const { db: triggeredDb } = triggers.wrapDB(ctx)
db: wrapDatabaseWriter({}, triggeredDb, tenantRules(tenant), TENANT_RLS_CONFIG)
// (3) one-office convex/triggers.ts — RLS authorizes against the PRE-image,
// so ownership must also hold on the POST-image. Registered for every tenant table.
export const rejectTenantReassignment = async (_ctx, change) => {
  if (change.operation === 'insert' && !change.newDoc.tenant) throw CROSS_TENANT_REFERENCE
  if (change.operation === 'update' && change.oldDoc.tenant !== change.newDoc.tenant)
    throw CROSS_TENANT_REFERENCE // 'Tenant ownership cannot be reassigned'
}
Why layer 4 exists at all is the best lesson in the codebase: RLS modify checks the document you're changing (pre-image). Without the trigger, a mutation could legally load its own tenant's row and patch tenant to another org's id — a write RLS happily allows. Every layer covers a hole in the previous one. That's the mindset tenancy requires.

Part 3 — How this lands in cvx-kit

The dividing line — and it's the same line the kit already draws for auth — is mechanism in the kit, policy in the host. WorkOS, the JWT claim shape, permission slugs: policy, injected. Field injection, RLS generation, trigger invariants, builder wiring: mechanism, and today every consumer would have to hand-roll all of it. Proposal, in kit-API terms:

3a. tenantTable in cvx-kit/zod-table

export const <entities> = tenantTable('<entities>', (id) => ({ ... }), {
  commandFields: [...], publicFields: [...],
})
// = zodTable + { tenant: z.string().min(1) } baked in, exactly like timestamps:
//   • excluded from insertSchema/commandInput (server-owned, like createdAt)
//   • stripped from updateSchema — tenant is immutable at the type boundary
//   • never in publicDto unless explicitly allowlisted

This mirrors the kit's existing timestamp opinion precisely: a server-owned field, injected once, unwritable from any client-facing mask.

3b. A tenancy module: registry → rules + trigger

// cvx-kit/tenancy (new export)
export function createTenancy<DataModel>(config: {
  tables: readonly TableNamesInDataModel<DataModel>[]  // THE registry
}) {
  return {
    tables,                                  // re-exported for tests
    rules: (tenant) => ...,                  // deny-default RLS map, generated
    registerGuards: (triggers) => ...,       // rejectTenantReassignment on every table
    requireTenantReference: ...,             // 404-not-403 cross-reference guard
  }
}

One registry drives everything — the property that made one-office safe is that adding a table to the registry is the entire onboarding; there is no second place to forget.

3c. Tenant-aware constructors via createAuthFunctions

createAuthFunctions<DataModel>({
  ...,
  tenancy: {                                  // optional — absent = today's behavior
    tenancy,                                  // the createTenancy(...) instance
    resolve: (bundle) => bundle.org.organizationId,  // policy: claim → tenant, injected
  },
})
// adds: tenantQuery, tenantMutation, tenantAction, tenantSystemMutation
// ctx gains ctx.tenant; mutation db is wrapped triggers → RLS(deny);
// insert paths stamp tenant from ctx — handlers never write it

The auth bundle already carries org.organizationId — the kit already resolves the org from the JWT and refuses requests without one. The tenant is one resolve away. Keeping tenancy optional means the single-org administration apps (your origin app) change nothing, and a multi-tenant app opts in with ~10 lines.

3d. Alignment that already exists

Two kit pieces anticipated this design and need no change, only documentation:

  • Approvals' scopeRef is the tenant slot. The component was already built tenancy-agnostic — pass ctx.tenant as scopeRef and per-tenant approval isolation falls out.
  • Components take tenant as an explicit argument. one-office's rule — the host adapter is the only code allowed to supply it, always from ctx.tenant, never from client input — is exactly the kit's existing "opaque validated data across the component boundary" rule.

3e. What stays out of the kit

ConcernWhy it stays host-side
Org switching, invitations, membershipsIdentity-provider surface (WorkOS UI + webhooks). The kit sees only "the claim changed".
Permission catalogs (erp.sales.manage…)Product vocabulary. The kit's role constructors are the extension point; a permission-claim check plugs into mapRole/role gates.
Tenant provisioning/archivalA webhook-driven domain command in the host (one-office: idempotent provisionOrganization).
Global/private tablesDeliberately outside the machinery. The kit's job is to make the registry split visible (docs + a conventions rule), not to guard what it can't see.
The honest footguns to document with the feature — all learned the hard way in one-office: (1) actions have no db, so action→internal handoffs must pass the server-derived tenant, never a caller value — the internal builders should be asserted to not accept a tenant arg; (2) provider ids (memberships, invitations) are global — org-scoped mutations must re-check ownership against the active org or you ship a cross-tenant IDOR; (3) private/global tables get none of the machinery — every one is a per-handler-discipline zone and should be rare and named; (4) cross-reference loads must return "not found", never "forbidden" — existence is also tenant data.

Suggested order of work

  1. Docs first (no code risk): rewrite conventions.md/architecture.md to module grain + sibling rules/queries rule + optional application/ layer.
  2. tenantTable in zod-table (small, additive, mirrors timestamps).
  3. cvx-kit/tenancy: registry → rules/guards/reference-check.
  4. tenancy option in createAuthFunctions + the tenant* constructors (the only intrusive piece — wrap order triggers→RLS, ctx branding, insert stamping).
  5. Architecture-test recipes in the docs: registry exhaustiveness, raw-builder ban already exists — add "tenant tables use tenantTable" and "internal builders accept no tenant arg".

Steps 1–3 are safe to ship in a patch release; step 4 deserves its own minor version and a design pass on the ctx type (one-office's unexported unique symbol branding is worth copying so a "tenant ctx" can't be hand-assembled).
