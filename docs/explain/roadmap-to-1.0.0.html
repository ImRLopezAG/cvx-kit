Subject
The release roadmap from 0.0.8 to 1.0.0, as defined in ROADMAP.md — what each milestone means, why it's ordered this way, and what "stable" will actually promise

The one-sentence version: the roadmap is not a feature list — it's a controlled shutdown of your freedom to break things. Every milestone closes one class of change you're currently allowed to make, until at 1.0.0 the only thing left open is additive.

Why now, and why this order

In one week, cvx-kit shipped four breaking changes as patch releases: the required internalQuery builder, the facade lockdown, the component mount-path change, and the tarball reshape. All correct, all fine — because you are the only consumer. The moment a second project installs the package, each of those becomes a broken build on someone else's machine with no semver signal warning them. A roadmap to 1.0.0 is really an answer to one question: in what order do we give up which freedoms?

The milestones, and what each one really is

0.1.0
The big one — consolidation AND the full feature set. One release that closes the breaking window and ships every planned helper, so a consumer adopts a complete kit once instead of chasing minors — and every feature lands already conforming to the frozen names. Consolidation: the package name decision (cvx-kit is a working title — the only item that gets more expensive with every install), the API-audit pass against conventions.md's own naming grammar, typed middleware context accumulation, CHANGELOG, and breaking-only-on-minor from here on. Features, all six: the pagination bridge (paginated(table.publicDto) + include(...).paginate(opts) — cursors, not just bounded take); the CRUD command factory (createCrudCommands(table, policy) — the standard create/update/archive operations from a zodTable's masks, the single biggest per-entity boilerplate left); the state-machine helper (createStateMachine(STATES, transitions), typed against the constants tuple, dropping into command guards); the rate-limit middleware factory (the first official middleware, over @convex-dev/rate-limiter, keyed by ctx.tenant); the webhook boundary helper (signature verification + natural-key dedup + system* delegation); and the agent tool generator (createAgentTools from the existing tools.* masks — agents get audited commands, never raw db access). Each ships with docs, runtime tests, and an llms.md entry.
0.2.0
Rules become tests. Everything conventions.md prescribes in prose — no raw builders outside functions.ts, no inline enums, no sibling-domain imports, facades mount once — becomes an importable createArchitectureTest(rules) a consumer runs on day one. This is the origin app's deepest lesson: a rule that exists in prose but not in the suite is a request, not a rule. Includes the tenancy-registry exhaustiveness helper, the llms.md conformance check (every export in its tables must exist with that signature — built here, reused as an rc gate), and the copyability test (copy a component to a tmpdir with only its package deps, run tsc) joining the permanent suite. Guardrails come after 0.1.0 on purpose: architecture tests freeze names into consumers' suites, so they must enforce the already-frozen vocabulary.
0.3.0
The first hour is generated. The WorkOS scaffold (auth.ts, auth.config.ts, http.ts, functions.ts, foundation.ts, triggers.ts from one command), audit facade helpers, and the final go/no-go on an idempotency component — deferred, and only revived if a consumer demonstrates a need beyond Convex's own exactly-once mutation delivery.
1.0.0-rc
Gates, not features. Nothing new ships here; the rc exists when facts are true: two real applications on the latest kit for weeks, one full minor cycle needing zero breaking changes, an automated check that llms.md's export tables match the real API, a CI matrix across bun/node and the convex peer range, and every exported runtime symbol exercised by at least one test. If a gate can't be met, that's information — the API wasn't ready, and the rc waits.
1.0.0
The promise. Frozen export surface, a written semver contract (what counts as breaking; deprecations live one minor with warnings), and MIGRATING.md from 0.x. From here, a consumer can ^1.0.0 and sleep.

What is deliberately NOT on the road

ExcludedWhy the decision is already made
General idempotency storeConvex's client already delivers exactly-once execution per mutation call; UI double-submission and webhook retries are boundary-local problems with natural keys. Decided this week — the roadmap records it so a future contributor doesn't relitigate it.
Frontend/React bindingsThe kit is a backend architecture; the client surface is Convex's own.
Multi-provider auth abstractionsThe injected-policy seam (getAuthUser / mapRole / verifyMembership) already accepts any provider — an abstraction layer above it would be speculation.

Candidates — recorded, not committed

Two ideas parked with reasons on file, so they're remembered without blocking any milestone: observability sink adapters (OTel/Axiom-shaped formatters for the injectable emit, so command.execution events land in real telemetry without per-consumer mapping) and a migration companion (a thin @convex-dev/migrations wrapper aligned with zodTable epochs — "make optional field required after backfill" as a declared step, closing the loop with migration.md's zero-downtime section). Either graduates into a milestone when a consumer actually needs it.

The ordering logic worth internalizing: consolidation (0.1) must precede guardrails (0.2) because architecture tests freeze names into consumers' test suites — enforcing conventions you're about to rename would double the migration. Guardrails must precede scaffolding (0.3) because a generator that emits code the architecture tests reject is worse than no generator. And the rc gates come last because they are the only part you can't do by writing code — they require calendar time under real load, which is why starting them early buys nothing.
Where this lives: the actionable version with checkboxes is ROADMAP.md at the repo root (linked from the README); this explainer is the "why" behind it. When a milestone's items are all checked, the release that closes it is the version in its heading.
