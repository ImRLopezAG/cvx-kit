# Authoring Convex components with cvx-kit

A component owns its schema, generated data model, foundation, function builders
and trigger registry. Use cvx-kit inside that boundary just as in an app domain.
The app authenticates callers and supplies trusted, validated scope arguments;
the component does not import the app's domains, auth singleton or environment.

## Layout

```text
<convex root>/components/outbox/
  convex.config.ts
  _generated/             # generated by Convex for this component
  schema.ts              # zodTable shapes and defineSchema assembly
  table.ts               # table indexes
  foundation.ts          # createEffectFoundation
  errors.ts              # defineErrorContract
  triggers.ts            # component-local registry and registrations
  functions.ts           # wraps this component's generated builders
  intents/
    contracts.ts
    commands.ts
    queries.ts
  client.ts              # optional host-facing facade
```

```ts
// components/outbox/convex.config.ts
import { defineComponent } from 'convex/server'
export default defineComponent('outbox')
```

The lint plugin recognizes `components/<name>/` under its configured `convexDir`.
It also discovers other component roots by parsing `convex.config.ts` for a
`defineComponent` call imported from `convex/server` (including renamed imports
and namespace calls). No config is executed. For generated or indirect config,
set `componentDirs` explicitly, relative to `convexDir`, on each enabled rule.

## Schema and indexes

```ts
// components/outbox/table.ts
import { z } from 'zod'
import { zodTable } from 'cvx-kit/zod-table'

export const intents = zodTable('intents', () => ({
  key: z.string(),
  payload: z.string(),
}))
export const tables = {
  intents: intents.table.index('by_key', ['key']),
}
```

```ts
// components/outbox/schema.ts
import { defineSchema } from 'convex/server'
import { tables } from './table'
export default defineSchema(tables)
```

For separate shape files, declare each table in `<entity>/schema.ts`, import
those declarations into component-root `table.ts`, then assemble that map in
component-root `schema.ts`. Keep dependencies one-way to avoid a schema/table
import cycle. `tenantTable` and `zodVariantTable` are also supported in component
`schema.ts`/`table.ts`. Attach indexes in `table.ts`. Raw `defineTable` remains
allowed in either file for existing components.

`zodTable` always injects optional `createdAt`, `updatedAt` and `archivedAt`.
They are reserved and excluded from insert/update inputs; no opt-out exists.
Register `timestamps` to fill created/updated times. `archivedAt` remains an
application-controlled soft-delete field. See [zod-table](../../skills/cvx-kit/references/zod-table.md).

## Foundation, errors and contracts

```ts
// foundation.ts
import { createEffectFoundation } from 'cvx-kit/effect'
export const { Command, Query } = createEffectFoundation({
  observability: {
    enabled: false,
    classifyError: () => ({ outcome: 'failed', errorCode: 'OUTBOX_FAILED' }),
  },
  writeAudit: () => undefined,
})
```

Choose an audit writer appropriate to the component when audit evidence is
required. A no-op writer deliberately records nothing.

```ts
// errors.ts
import { defineErrorContract } from 'cvx-kit/errors'
export const outboxErrors = defineErrorContract({
  INTENT_NOT_FOUND: { message: 'Intent not found', details: {} },
})
```

```ts
// intents/contracts.ts
import { z } from 'zod'
import { defineDomainContract } from 'cvx-kit/contracts'
import { intents } from '../table'
import { outboxErrors } from '../errors'

export const intentContract = defineDomainContract({
  errors: outboxErrors,
  commands: {
    create: {
      input: intents.insertSchema,
      result: intents.schema,
      classification: 'business',
    },
  },
  queries: {
    read: {
      input: z.object({ id: intents.schema.shape._id }),
      result: intents.schema.nullable(),
    },
  },
})
```

```ts
// intents/queries.ts
import type { QueryCtx } from '../_generated/server'
import { Query } from '../foundation'
import { intentContract } from './contracts'
export const intentsQueries = Query({
  contract: intentContract,
  context: (ctx: QueryCtx) => ctx,
  operations: ({ query }) => ({
    read: query.handler(({ id }, ctx) => ctx.db.get(id)),
  }),
})
```

Use `Command`/`Query` with the component's own generated `MutationCtx`/`QueryCtx`.
Promise handlers and Effect handlers returning native component documents both
fit the derived result schema; component `Id<'intents'>` is compatible. There
is no need to cast documents, turn IDs into unbranded strings, or weaken Effect
builder checks. See [domain operations](../../skills/cvx-kit/references/domain-operations.md) for registries.

The injected timestamps are **optional in the data model** even when triggers
populate all new rows. A result contract that requires a timestamp rejects a
raw `Doc<'intents'>` handler at compile time, correctly: old or unwrapped rows
may lack that field. Retain `intents.schema` for full rows, or deliberately
validate/narrow with `requiredResult.parse(row)` after handling `null`. Backfill
old data before promising required timestamps. Do not use non-null assertions
on timestamp fields to silence this mismatch.

For a DTO that hides timestamps, derive a projection and actually parse it:

```ts
const result = intents.schema
  .omit({ createdAt: true, updatedAt: true, archivedAt: true })
  .strip()
// Return result.parse(row), or let the operation's result decoder strip them.
```

`omit` alone retains a strict object's rejection of extra keys. `.strip()` is
an explicit boundary choice. For public data, prefer a field allowlist via
`publicFields` and `toPublicDto`; removing timestamps does not redact secrets.

## Triggers and function builders

```ts
// triggers.ts
import { createTriggers, timestamps } from 'cvx-kit/triggers'
import type { DataModel } from './_generated/dataModel'

export const triggers = createTriggers<DataModel>()
timestamps(triggers, 'intents')
triggers.register('intents', async (ctx, change) => {
  if (change.operation === 'insert') {
    // Component-local invariant or denormalization; ctx.db is trigger-wrapped.
  }
})
```

```ts
// functions.ts
import { NoOp } from 'convex-helpers/server/customFunctions'
import { zCustomMutation, zCustomQuery } from 'convex-helpers/server/zod4'
import { effectZodApiBuilder } from 'cvx-kit/effect'
import { triggerContext } from 'cvx-kit/triggers'
import { mutation, internalMutation, query } from './_generated/server'
import { triggers } from './triggers'
import { outboxErrors } from './errors'

export const componentMutation = effectZodApiBuilder(
  zCustomMutation(mutation, triggerContext(triggers)),
  { errors: outboxErrors },
)
export const componentInternalMutation = effectZodApiBuilder(
  zCustomMutation(internalMutation, triggerContext(triggers)),
  { errors: outboxErrors },
)
export const componentQuery = effectZodApiBuilder(
  zCustomQuery(query, NoOp),
  { errors: outboxErrors },
)
```

Use these builders to export the component's functions, delegating to the local
registries. For example, `functions.ts` can export `read` with the contract's
input/result and `handler: (ctx, args) => intentsQueries.exec('read', args, ctx)`.
Export `create` similarly over the local Command registry; that is the function
the host enqueue facade below calls. See the tested pattern in
`test/component-support.test.ts` in the cvx-kit repository.

`triggerContext` also works with `customMutation`. It replaces only `ctx.db`;
it does not authenticate the caller. Register all triggers once in the local
`triggers.ts`. Every public and internal mutation must use the wrapped builder.
Do not stack it with a second wrapper around the same registry. Queries and
actions do not expose a mutation writer; action writes go through wrapped
mutations. A throwing trigger aborts and rolls back the transaction.

Equivalent existing wiring remains valid:
`customCtx((ctx: MutationCtx) => triggers.wrapDB(ctx))`. The helper removes the
repeated context annotation and returns only the database customization.
Seeding via convex-test's `t.run` bypasses function builders and triggers.
See [triggers](../../skills/cvx-kit/references/triggers.md).

Pass the **same** error contract to the foundation operation contract and the
Effect API builder. Host error policies may need to include component failures
when forwarding them across another API boundary; unknown errors remain redacted.

## App mounting and auth

```ts
// <convex root>/convex.config.ts
import { defineApp } from 'convex/server'
import outbox from './components/outbox/convex.config'
const app = defineApp()
app.use(outbox)
export default app
```

Only the app's server can call mounted component functions. Export a client
facade when app domain code needs access; the app's root `convex.config.ts`
may import component configuration directly. Do not import private component
implementation files into host domains. Use generated references inside a
host facade. Keep the delegation in the component client and instantiate it
once at the app root:

```ts
// components/outbox/client.ts
import type { GenericDataModel, GenericMutationCtx } from 'convex/server'
import type { ComponentApi } from './_generated/component'

export function createOutbox(component: ComponentApi) {
  return {
    enqueue: (
      ctx: Pick<GenericMutationCtx<GenericDataModel>, 'runMutation'>,
      key: string,
      payload: string,
    ) => ctx.runMutation(component.functions.create, { key, payload }),
  }
}
```

```ts
// <convex root>/outbox.ts
import { components } from './_generated/api'
import { createOutbox } from './components/outbox/client'
export const outbox = createOutbox(components.outbox)
```

Call `outbox.enqueue(ctx, key, payload)` through the app's authenticated API constructor, check tenant
membership/authorization there, and derive actor/scope from the trusted auth
context. If the component accepts tenant or actor fields, pass them from that
context rather than accepting caller-supplied authority. Treat host IDs as
opaque validated strings across component boundaries; the component's own
foreign keys use its own generated IDs. See [auth](../../skills/cvx-kit/references/auth.md).

## Lint configuration

Load `cvx-kit/oxlint` using the configuration in [oxlint](../../skills/cvx-kit/references/oxlint.md). For Accord,
use `convexDir: 'src'` when cwd is `apps/convex` (or its full repo-relative path
when lint runs from the monorepo root). Remove the component schema rule-off
override. Ordinary `components/<name>` needs no additional option.

```json
{
  "cvx/domain-import-boundaries": ["error", {
    "convexDir": "src",
    "domainPublicFiles": {
      "communication": ["helpers/delivery"]
    }
  }],
  "cvx/schema-file-boundaries": ["error", { "convexDir": "src" }],
  "cvx/no-raw-builders": ["error", { "convexDir": "src" }],
  "cvx/no-manual-timestamps": ["error", { "convexDir": "src" }]
}
```

`domainPublicFiles` extends only cross-domain imports of the named module's
public files. Entries are exact paths relative to `domain/<module>`, without
extensions, and work after resolving relative imports or tsconfig aliases.
The default public files remain `rules`, `queries`, `contracts`. This option
does not allow reverse API/application imports, migration imports, or imports
from `domain/shared` into ordinary domains. Prefer moving reusable decisions
into `rules.ts` or `queries.ts`; list an extra file only when it is a deliberate
public API. Components use `component-boundaries`, independently of host layers.

Component-aware rule behavior:

| Rules | Component behavior |
| --- | --- |
| `schema-file-boundaries` | Zod/raw tables in schema/table files; kit table indexes in `table.ts`. |
| `no-raw-builders` | Only component-root `functions.ts` imports raw builders. |
| `root-facade-ownership` | Component-local `foundation.ts`, `functions.ts`, `triggers.ts`, etc. own infrastructure. |
| `no-manual-timestamps`, `no-unbounded-reads` | Same protection as app code. |
| `domain-file-responsibilities` | Pure rules, read-only queries, declarative schemas, external I/O in actions. |
| `component-boundaries`, `no-component-env` | Isolation and injected configuration still apply. |
| `domain-import-boundaries` | Host layering does not apply inside a component; component isolation does. |
| `reserved-domain-file-anatomy` | Still specific to host `domain/` registries; component files may also export API adapters. |
| Host root/project/API rules | Keep their existing app-root and `api/` scope. |
| Remaining vocabulary, DTO, pagination, reference and export rules | Keep their existing checks; no component exemption. |

These stricter checks can expose existing component timestamp writes, unbounded
reads and raw builders. Migrate those calls to the local facades and triggers
instead of disabling the rules.
