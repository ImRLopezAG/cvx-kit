# Migrating to cvx-kit 2

cvx-kit 2 removes Zod from the kit. Apps on cvx-kit 0.1.x (v1) declare schemas with `z`, tables with `zodTable` and `zid`, contracts with `zodContract` and Effect APIs with `effectZodApiBuilder`. In 2.0 they declare schemas with `k`, tables with `kTable` and a plain field object, contracts with `kContract` and Effect APIs with `effectApiBuilder`. Convex receives plain native validators, and a function module that imports no Zod loads much less code on every call. Stored data does not change: a v2 table stores the same shape and indexes as the v1 table it replaces, so no data migration is expected. Every app on v1 needs this guide; the v1 names are gone, so the whole Convex project moves in one branch.

The steps, in order: [update dependencies](#prerequisites), [run the codemod](#the-codemod), fix what it reports using the [name map](#name-map), the [Zod to `k` map](#zod-to-k-map) and the [behaviour changes](#behaviour-changes), then [verify](#verification-checklist). The `k` API is in [k](k.md) and tables are in [table](table.md).

## Prerequisites

| Package          | 2.0 requirement                                      |
| ---------------- | ---------------------------------------------------- |
| `convex`         | `^1.46.0` (peer)                                     |
| `convex-helpers` | `>=0.1.130 <0.2.0` (peer)                            |
| `effect`         | `>=4.0.1 <5`, optional; needed for `cvx-kit/effect`  |
| `react`          | `^18 \|\| ^19`, optional; needed for `cvx-kit/react` |
| `zod`            | `^4.6.7`, optional; needed only for `cvx-kit/zod`    |

Zod is no longer required. Remove it from the app's dependencies once no app code imports it. Keep it if app code still parses external data with Zod or uses `cvx-kit/zod`.

```sh
bun add cvx-kit@^2
# or: npm install cvx-kit@^2
```

## Coming from before 0.1.31 or 0.2.0

An app moving to 2.0 from a release before 0.1.31 or 0.2.0 also crosses the behaviour changes of those releases. None of them is a type error, so check each one ([upgrading](upgrading.md) has the details):

| Since  | Change                                                                                                                                                                                                                                                                                                           | To keep the old behaviour                                                                                        |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 0.1.31 | `nestedAudit: 'fold'` is the default: an Effect command nested under an operation that declares an audit callback writes no audit entry of its own; the outermost entry stands for the request. A bulk command that `exec`s one nested command per row used to write one audit entry per row and now writes one. | `createEffectFoundation({ nestedAudit: 'separate' })`, then remove any `nestedAudit` flag from bound contexts.   |
| 0.1.31 | `projectErrorCause` (and the Effect API adapters' `errors` projection) projects a trusted declared error thrown inside `Effect.gen` (`throw errors.create(...)`) to its `DeclaredFailure` instead of `UnknownFailure`. Clients that matched `UNKNOWN_FAILURE` for those errors now receive the declared code.    | No setting; return `yield* fail(...)` or map the cause yourself if a declared error must stay hidden.            |
| 0.2.0  | `argumentFailure` decides what an argument rejection throws. Its 0.2.0 default `'legacy'` (`ConvexError({ ZodError })`) is gone in 2.0; the default is `'validation'` (`KValidationError`).                                                                                                                      | `argumentFailure: 'declared'` for the `INVALID_ARGUMENTS` envelope, or a function returning the app's own error. |
| 0.2.0  | Peer ranges: `zod ^4.6.7` (only for `cvx-kit/zod` in 2.0) and `convex-helpers >=0.1.130 <0.2.0`.                                                                                                                                                                                                                 | None; upgrade the peers.                                                                                         |

## Behaviour changes

### Validation failures have a kit-owned shape

Before, a failed arg parse threw `ConvexError({ ZodError: issues })`. Now every validation failure the kit raises (declared checks on args, compact filter boundaries, search options, `parse`, `toPublicDto`) is a `KValidationError`: a `ConvexError` whose data is `{ code: 'VALIDATION', issues }`, each issue `{ path, code, message }`. Structural arg failures (a wrong type, a missing field, an unknown key) are raised by Convex itself before the kit runs, with Convex's own error.

```ts
// before
if (error instanceof ConvexError && 'ZodError' in error.data) showIssues(error.data.ZodError)

// after
if (error instanceof ConvexError && error.data?.code === 'VALIDATION') showIssues(error.data.issues)
```

What to do: update server code and clients that read `ZodError`. Issue messages and some codes differ from Zod's (for example `not_integer` where Zod said `invalid_type`, and one `unrecognized_key` issue per unknown key where Zod reported one `unrecognized_keys` issue on the object).

Search option failures that v1 reported as `SearchError('SEARCH_OPTIONS_UNSUPPORTED')` for out-of-range values (for example a non-positive `numItems`) are now `VALIDATION` errors. Unsupported option combinations still throw `SearchError`.

### `safeParse` returns issues, not an error

```ts
// before
const result = schema.safeParse(input)
if (!result.success) log(result.error.issues)

// after
const result = schema.safeParse(input)
if (!result.success) log(result.issues)
```

### Unknown keys

`k.object` strips unknown keys when application code calls `parse`, `safeParse` or Standard Schema `validate`, like `z.object`. Function `args` and `returns`, table fields and writes, `kContract`, contract inputs and results of the command and query registries (Effect ones included), CRUD masks, filters and cursors still reject unknown keys. Native Convex object validators remain closed.

```ts
k.object({ a: k.string() }).parse({ a: 'x', b: 1 }) // { a: 'x' }
k.strictObject({ a: k.string() }).parse({ a: 'x', b: 1 }) // throws: unrecognized_key at ['b']
k.object({ a: k.string() }).strict().parse({ a: 'x', b: 1 }) // same rejection
```

Strictness is per object: a strict parent does not change a nested object's policy. `pick`, `omit`, `extend`, `partial` and `required` keep the receiver's policy. `.loose()` keeps unknown keys during parse. Explicit `.strip()` also makes the kit's full parse strip (for example inside `.catch` or under `skipConvexValidation`) and omits `additionalProperties: false` from input-side JSON Schema. A plain `k.object` still emits that JSON Schema restriction to describe the boundary. Neither `.strip()` nor `.loose()` opens the native Convex validator; see [Open objects](k.md#open-objects).

Table-derived schemas (`insertSchema`, `updateSchema`, `commandInput`, `dto()`, `tools`) and literal-key records are `.strict()` objects, so a direct `parse` of them rejects unknown keys as v1's did. In a `k.union`, parse prefers a member that accepts every key over an earlier one that would strip some; Zod takes the first match.

Contract results reject unknown keys at any depth. In v1 a contract `result: z.object({...})` stripped whatever else the handler returned; in v2 the registry decodes the result with the strict boundary parse, so an extra key fails the call with an `unrecognized_key` issue. Foundation and Effect registries both surface it as a `VALIDATION` error with the issue paths; a schema wrapped in `kContract` fails with a typed `ContractValidationError` in Effect instead. TypeScript does not flag it, because excess-property checks apply only to object literals. Find each handler that returns a row or a wider object and do one of these:

- Return only the declared fields: `toPublicDto(row)` for a table row, or build the object yourself.
- Declare the result object with `.strip()` to drop the extra keys at the contract boundary, as v1 did. The policy is per object, so a nested object needs its own `.strip()`.

```ts
// contract: result: k.object({ id: k.string() })
// handler returns { id, secret } → VALIDATION, unrecognized_key at ['secret']
result: k.object({ id: k.string() }).strip(), // strips secret, as v1 did
```

**If you migrated with the beta.0, beta.1 or beta.2 codemod:** it rewrote every `z.strictObject(...)` and `.strict()` to a plain `k.object(...)`, which was strict then. On beta.3 each of those strips unknown keys under an application `parse`, with no type error, and the source no longer says which ones were strict. Kit boundaries still reject, so only objects parsed directly are affected: validators of server functions, webhooks and other untrusted input outside the kit. The codemod can restore them from the commit before the migration:

```sh
npx cvx-kit-codemod-v2 apps packages --restore-strict <pre-migration-ref>          # dry run
npx cvx-kit-codemod-v2 apps packages --restore-strict <pre-migration-ref> --write
```

In this mode it rewrites nothing else. It reads each file as it was at the ref, pairs its Zod object factories with the file's current ones (first by the binding and property path that holds the object and its field names, then by field names alone when they are unique on both sides), and turns each `k.object` whose Zod original was `z.strictObject` or ended in `.strict()` into `k.strictObject`. It lists what it could not do, with line numbers in the file at the ref: `strict-on-reference` (`Base.strict()` on a variable: add `.strict()` to the `k` schema by hand), `strict-unpaired` (the object's fields changed or it moved to another file), `strict-ambiguous` (several objects have the same fields, so the codemod cannot tell which one was strict) and `strict-now-other-policy` (the object now says `.strip()` or `.loose()`, or is a `k.strictObject(...)` with a later policy call). The [codemod's reason codes](#the-codemod) table lists them. Files that did not exist at the ref are left alone, and a second run changes nothing.

Since beta.3, code that depended on `unrecognized_key` from application `parse`/`safeParse` must add `.strict()` or use `k.strictObject`. Existing `.strip()` calls still work and can be removed where their only purpose was to restore Zod's parse behaviour.

### Parse returns the input when nothing is normalised

`z.object(...).parse` returned a new object in schema key order. A `k` parse returns the input object itself when nothing is normalised (no default filled, no normaliser or transform changed a value, no key stripped), so the result is `===` the input and keeps the input's key order. Code that compares `JSON.stringify(schema.parse(a))` with a stored string, uses the output as a cache key, or mutates the output changes behaviour. Sort keys before serialising, or copy the result (`{ ...schema.parse(a) }`) before mutating it. See [Parse and issues](k.md#parse-and-issues).

### Derived objects refuse to drop object-level checks

`pick`, `omit`, `extend` (also `extend({})`), `partial` and `required` build a new object over the same field schemas; field checks are kept. On an object with a `refine`, `check` or `overwrite` declared on the object itself, they throw at declaration instead of silently dropping it: `k: extend() would drop 1 object-level check(s); pass { dropChecks: true } or { keepChecks: true }`. Zod kept refinements through `extend` in some versions and dropped them in others, and Zod 4 throws on `.pick`/`.omit` of a refined object.

What to do: at each site, pass `{ dropChecks: true }` as the last argument to drop the checks (`schema.pick('a', 'b', { dropChecks: true })`), or on `extend`, `{ keepChecks: true }` to run them on the extended object. The codemod reports each mask or extend call on a refined object it can see as `derive-drops-checks`.

### Table boundaries and object spread

A table boundary's `table`, `schema`, `publicDto` and the other derived members are built on first read. An object spread copies them, so `{ ...table, table: other }` is a working boundary with one member replaced; it builds every boundary of that table at the spread. 2.0.0-beta.0 dropped them in a spread, and the copy failed at first use in relations (`Expected matching discriminated union boundaries`). See [Replacing a member](table.md#replacing-a-member).

### Kit validation can report what Convex's argument check reported

Where the kit parses a value in full, an illegal value that v1 left to Convex's argument check (a wrong type, an unknown key, a record key Convex rejects) is reported by the kit as a `VALIDATION` error with issues. This happens with `skipConvexValidation: true`, Effect inputs, compact filter boundaries, contracts and explicit strict parses, and for a record key that a normaliser turns into a key Convex rejects. Clients that match Convex's `ArgumentValidationError` text should also handle `{ code: 'VALIDATION', issues }`.

### Class instances

`k.object` accepts class instances during application parse, reading only own enumerable properties into a fresh plain object. Inherited fields and prototype getters count as missing, and the output does not retain the instance's prototype. An explicit `.strip()` is no longer needed for this. See [Class instances](k.md#class-instances).

### Return values are not parsed or stripped

v1 parsed every handler result through the `returns` schema, which stripped extra fields and ran transforms and refinements. In 2.0 the kit exports the output-side native validator and Convex validates the returned value. A handler that returns more fields than `returns` declares now fails Convex's return validation. TypeScript does not find these handlers: an excess property is a type error only in an object literal, not in a returned row. convex-test reports the failure only when a test calls that function, so search for handlers that return rows or spread objects.

```ts
// before: returned the whole row; v1 stripped secretNote
handler: async (ctx, { id }) => ctx.db.get(id),

// after: project the row
handler: async (ctx, { id }) => {
	const row = await ctx.db.get(id)
	if (!row) throw new KitError({ code: 'NOT_FOUND' })
	return documents.toPublicDto(row)
},
```

What to do: return `toPublicDto(row)` for table rows, or build the object with the declared fields (`schema.pick(...)` gives the shape; pick the values yourself). A `returns` schema with a transform is rejected when the validators are exported. A `transform` or `pipe` schema reused as a contract `result` type-checks, so declare results with their output types (see [Transforms](k.md#transforms)). Refinements on a `returns` schema do not run. `returns` must be a schema (`k.object(...)`, `v.object(...)`, `documents.publicDto`), not a plain field object.

With `skipConvexValidation: true` nothing checks a function's `returns`: Convex's own check is off and the kit does not parse return values. v1 parsed them in that mode. If a function relied on that, validate the value in the handler (`schema.parse(result)`) or leave Convex validation on.

### Transforms are input-only

`transform` and `pipe` (and the date conversions) are allowed on function args, command inputs, contract inputs and `parse`. They are rejected on table fields (a type error and an error when the table is defined) and on `returns`. The normalisers `trim`, `toLowerCase`, `toUpperCase` and `overwrite` are allowed everywhere.

```ts
// before: a table field that transformed
zodTable('items', () => ({ code: z.string().transform((s) => s.toUpperCase()) }))

// after: a normaliser keeps the type and is allowed
kTable('items', { code: k.string().toUpperCase() })
```

What to do: replace type-preserving transforms with `trim`/`toLowerCase`/`toUpperCase`/`overwrite`. Move type-changing transforms into function args (v1 stored a transformed field as its input type anyway).

### Refinements and checks are synchronous

`superRefine` becomes `check`. Async refinements and transforms are not supported: a `refine` callback that returns a promise fails with an `Invalid input` issue.

```ts
// before
z.object({ a: z.number(), b: z.number() }).superRefine((value, ctx) => {
	if (value.a > value.b) ctx.addIssue({ code: 'custom', message: 'a > b', path: ['b'] })
})

// after
k.object({ a: k.number(), b: k.number() }).check((value, ctx) => {
	if (value.a > value.b) ctx.addIssue({ message: 'a > b', path: ['b'] })
})
```

What to do: move database lookups and other async checks into the handler.

### Reads do not re-run normalisers

`toPublicDto`, `dto(...)` and the other read boundaries validate a stored row's shape and fill defaults, but they do not re-run normalisers (`trim`, `toLowerCase`, `toUpperCase`, `overwrite`) or checks on stored values. A row stored before a normaliser was added to its field comes back exactly as stored, for example with surrounding spaces or mixed case. v1's DTO parse ran them on read and hid such rows. The fix for old rows is a one-off data migration that rewrites them through the current schema (for example with `@convex-dev/migrations`, patching each row with `table.storage.parse(row)` minus the system fields); after it, writes keep them normalised.

### Defaults: patches no longer fill them

Defaults are stored optional (as in v1), filled on insert and command input, filled by `toPublicDto` on read, and required on public and return shapes. `updateSchema` and `.partial()` no longer fill defaults. In v1, `updateSchema.parse({})` filled every default, so a partial patch overwrote stored values; that was a bug.

```ts
// before: documents.updateSchema.parse({}) → { reviewState: 'draft' }
// after:
documents.updateSchema.parse({}) // → {}
```

What to do: nothing, unless code relied on a patch resetting fields to their defaults; set those fields explicitly.

### Tables take a plain field object

```ts
// before
import { z } from 'zod'
import { zodTable } from 'cvx-kit/zod-table'

export const documents = zodTable(
	'documents',
	(id) => ({ title: z.string(), ownerId: id('users') }),
	{ commandFields: ['title'], publicFields: ['title', 'ownerId'] },
)

// after
import { k } from 'cvx-kit'
import { kTable } from 'cvx-kit/table'

export const documents = kTable(
	'documents',
	{ title: k.string(), ownerId: k.id('users') },
	{ commandFields: ['title'], publicFields: ['title', 'ownerId'] },
)
```

Other table changes:

- `insert(...)`, `update(...)`, `pick` and `omit` take string keys: `documents.insert('secretNote')` instead of `documents.insert({ secretNote: true })`. The codemod rewrites `pick`/`omit` masks on schemas it can prove, but not `insert`/`update` call sites on tables.
- `table` and the schema boundaries are built lazily on first read, as enumerable accessors. An object spread copies them, so `{ ...documents, table: other }` is a working boundary with `table` replaced; the spread builds every boundary of that table at that point instead of on first use (see [Replacing a member](table.md#replacing-a-member)). Use `withFieldGroups(documents, fieldGroups)` from `cvx-kit/relations` for field groups. In 2.0.0-beta.0 a spread dropped these members, and the first use failed in relations with `Expected matching discriminated union boundaries`; upgrade past that beta.
- Ids need no shared helper registry. v1 kept id metadata in a convex-helpers instance registry, so two installed helper copies could turn an id into `v.any()`; `k.id` is a native `v.id` and has no such requirement.
- `tools.*` keep ids as `k.id(...)`. `toJsonSchema` renders them as strings, which is what `jsonSafeZid` existed for.
- A one-value enum, `k.json()`, every nullable/optional ordering, the timestamps and the tenant field are stored exactly as v1 stored them.

### Ids are branded on input

`k.input` keeps `Id<'table'>`. v1's `zid` accepted a plain `string` at the type level on input. Callers that pass ids typed as `string` (from URLs or forms) now fail to typecheck.

```ts
// after
const id = ctx.db.normalizeId('documents', raw) // Id<'documents'> | null
```

What to do: normalise external strings with `ctx.db.normalizeId('table', raw)` on the server, or type client values as `Id<'table'>` from the generated data model.

Across a component boundary, a host may declare `k.id('deliveries')` in a function even when `deliveries` belongs to a component and is absent from the root schema. A local backend trial pushed that declaration with `convex dev --once`; `convex function-spec` reported `{ "type": "id", "tableName": "deliveries" }`, as in v1. The migration work is branding the plain strings returned by the component for the host's typed callers. Use the component's return contract to establish the table, then brand that trusted result as `Id<'deliveries'>`; do not use the host's `ctx.db.normalizeId` for a table outside its generated data model. Keeping a reference as `k.string()` is also valid when the host does not need the brand.

```ts
// host
export const approvalRefs = kTable('approvalRefs', {
	approvalId: k.string(),
	orderId: k.id('orders'),
})
```

### Numbers accept NaN and Infinity

A bare `k.number()` accepts `NaN` and `±Infinity`, as native `v.number()` does; `z.number()` rejected them. Any `min`, `max` or `length` bound rejects `NaN`. `k.int()` and `k.number().int()` require safe integers: non-integers report `not_integer`, and integers below or above the safe range report `too_small` or `too_big`. `.safe()` remains available and is redundant on an integer schema.

```ts
const amount = k.number().finite()
const cents = k.int()
```

The codemod emits `k.int()` for `z.int()`, `z.number().int()` and `z.number().safe()`, without redundant `.safe()` calls. It keeps integer check options as `k.number().int(options)`. `z.number()` (with or without bounds such as `.min(0)`) becomes `k.number().finite()`, reported as `number-finite-preserved`. `--native-number-bounds` only omits the added `.finite()` and reports `number-now-accepts-nan`; integer safety is unchanged. Explicit `.finite()` calls remain.

A bare `k.number()` runs no kit check at a function boundary; `.finite()` and integer checks run kit code because native Convex numbers permit NaN, infinities and unsafe integers.

### Dates

`k.isoDate()`, `k.isoDateTime()` and `k.timestamp()` replace `z.iso.date()`, `z.iso.datetime()` and hand-written timestamp checks, with conversions (`toTimestamp()`, `toIsoDate()`, `toIsoDateTime()`) on input positions only. There is no date library in the kit. See [k](k.md#dates).

`k.isoDateTime()` accepts timezone offsets such as `2026-11-27T10:00:00+02:00`; bare `z.iso.datetime()` accepts only a `Z` suffix. The codemod rewrites the bare call to `k.isoDateTime()`, which widens accepted input. There is no option on `k.isoDateTime` to refuse offsets. To keep UTC-only input, use `k.isoDateTime().regex(/Z$/)` before any conversion such as `.toTimestamp()`. The regex checks the ISO string, not a parsed date or timestamp.

`k.timestamp()` accepts 1970-01-01T00:00:00.000Z through 9999-12-31T23:59:59.999Z only. A negative timestamp fails with `too_small`, so do not use `k.timestamp()` for dates before 1970; use `k.number().int()` or store an ISO string. A conversion outside the range, such as `k.isoDate().toTimestamp()` on `'1969-12-31'`, reports an `invalid_value` issue instead of throwing.

### Record keys follow Convex's rule

After the key schema runs (including normalisers), each `k.record` key must be non-empty, at most 1024 characters, printable ASCII, and must not start with `$` or `_`. Otherwise parse reports an `invalid_format` issue at that key. Convex already rejected such keys on write, so the error now comes from the kit before the write. A key normaliser such as `.toLowerCase()` that produces a key Convex would reject fails the same way.

For an object whose keys are arbitrary (`_id`, `_creationTime` included), use `k.jsonObject()`: a plain object of JSON values, natively `v.any()`, whose keys parse checks against Convex's object-value rule (no leading `$`). See [Open objects](k.md#open-objects).

### Shared arrays and field objects become read-only

Arrays and objects handed to `k.enum`, `k.union`, `k.discriminatedUnion`, `k.record` and `refine` options are frozen at declaration, and an object's field map is frozen the first time `.shape` is read. `k` holds them by reference rather than copying them. Code that later mutates a shared vocabulary tuple or field object (`STATUSES.push(...)`, `fields.extra = ...`) now throws in strict mode.

```ts
const STATUSES = ['open', 'done'] as const
const status = k.enum(STATUSES) // STATUSES is now frozen
const extended = k.enum([...STATUSES, 'archived'] as const) // spreading still works
```

Build a new array or object instead, or use `.extend(...)` for objects.

### Discriminator values must be unique

A `k.discriminatedUnion` whose options share a value (two equal literals, or an enum that overlaps another option's literal) throws when it is first used, for example on the first `parse` or the first call of a function that declares it. Run each such schema once in a test so the error shows in CI.

### An empty object input accepts no keys

For `const empty = k.object({})`, `k.input<typeof empty>` is `{ readonly [key: string]: never }`, so passing extra properties to an empty command input is a type error, as it was with a strict empty Zod object.

### Relations and querying

- `defineRelations` takes v2 table boundaries. Relation helpers are memoised and immutable.
- Search option failures are `VALIDATION` errors (see above).
- DTOs produced by the engine only validate; they do not transform.
- The Zod-internals fast path and its list of audited Zod versions are gone; any Zod 4 version works with `cvx-kit/zod`.

### Contracts and Effect

- `zodContract(schema)` becomes `kContract(schema)`. Callers supply `k.input<S>` and handlers receive `k.infer<S>`. Decoding is synchronous.
- `decodeContract(schema, value)` with a bare `k` schema resolves with `{ issues }` for invalid input, as `kContract` does; before, it rejected. Code that caught the rejection must read `result.issues` instead. Effect registries are unchanged: a bare `k` contract that fails still ends the operation with the `VALIDATION` error the client receives, and wrapping the schema in `kContract` remains the way to get a typed `ContractValidationError` that `Effect.catchTag` can recover.
- Contract results reject unknown keys; see [Unknown keys](#unknown-keys).
- `effectZodApiBuilder` becomes `effectApiBuilder`, which accepts both `k` schemas and native validators.
- `createEffectCrud` ids are `Id<'table'>`.
- `returns` must be a schema (`k.object(...)`), not a plain field object.

```ts
// before
returns: { ok: z.literal(true) },
// after
returns: k.object({ ok: k.literal(true) }),
```

### Agent tools

`AgentToolRecord.args` is a `k` schema. It implements Standard Schema v1 and parses with `args.parse`. Convert it for the agent library: `toJsonSchema(record.args)` from `cvx-kit/json-schema` for libraries that take JSON Schema, or `toZod(record.args)` from `cvx-kit/zod` for libraries that take Zod. See [agent-tools](agent-tools.md).

### Zod interop

`toZod(schema)` carries `refine`, `check`, `overwrite`, `transform` and `pipe`, so the Zod schema runs the same callbacks as `k` `parse`. Three differences come from Zod itself and remain: Zod's number rejects `NaN` and `Infinity` where `k.number()` accepts them unless `.finite()` is declared, `z.any()` (the converted `k.custom`) accepts `undefined` where `k` refuses it, and a Zod union takes its first matching member where `k` prefers a member that accepts every key. Import `toZod` from `cvx-kit/zod/classic` for classic Zod with chain methods, or from `cvx-kit/zod` for `zod/mini`. `.catch` is not carried and throws. `toZod` maps a `k` default to Zod's `prefault`, so the default runs through the rest of the chain (normalisers and checks) as it does in `k`; Zod's `default` would skip them. A default declared above a transform or pipe supplies parsed output, so it converts to Zod's `default`. A `partial()` field converts without its default, matching `k`, where a partial field stays omitted.

### Components

`approvalCallbackInput` is a `k.object` and `approvalCallbackArgs` is its native validator. Use `approvalCallbackArgs` as `args` of a native callback mutation, or `approvalCallbackInput` with the kit builders.

### Lint rules

The `cvx-kit/oxlint` rules recognise `k`, `kTable`, `kVariantTable`, `tenantTable`, `createModule` and the `cvx-kit/table` entry where they recognised `z` and `zodTable`. See [oxlint](oxlint.md).

### TypeScript limits

One compiler limit remains: `TS2590` (expression produces a union type that is too complex to represent). It has two shapes.

An object that embeds itself level after level, each level extending the previous one, doubles the field paths TypeScript tracks at every level. 15 such levels check and 16 do not, and hoisting does not help. Give one intermediate level an explicit type, which stops the paths from accumulating while the parsed type stays the same; `test/k-extend-depth-types.ts` in the kit shows the annotation.

A large inline `.extend({...})` inside `k.discriminatedUnion([...])` or `k.array(...)` can reach the limit much sooner. Hoist the extended object to a constant and pass the constant:

```ts
const cardPayment = basePayment.extend({ type: k.literal('card'), last4: k.string() })
const payment = k.discriminatedUnion('type', [cardPayment, bankPayment])
```

Two errors that earlier betas produced are fixed in 2.0.0-beta.7, so their workarounds can go:

- `TS2589` (type instantiation is excessively deep) on long `.extend` chains. It appeared at about 33 chained calls; 40 now check.
- `TS2589`, or `TS5114` (`SupportedNative` referenced circularly), where a query-engine handle (`querying(ctx).tasks`) was passed as a function argument, returned from a context function, or used after an Effect `yield*`. The filter types recursed forever on an unresolved union validator. It did not depend on the number of tables. Building the query inside the handler is no longer required.

## Constructs with no v2 form

These are not supported in 2.0. `cvx-kit/zod` does not help: it converts `k` to Zod, one way, so it cannot turn a Zod schema into a `k` schema.

| Construct                                                              | What to do                                                                                                                                                                                                                                           |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.catchall(x)`                                                         | Convex stored these as closed objects and rejected the extra keys on write. Use `.loose()` when parse should keep extra keys unchecked, a strict `k.object` with every field declared, or a `k.record(k.string(), value)` field for open-ended keys. |
| `z.lazy` (recursive schemas)                                           | Restructure: store a bounded depth explicitly (nested objects to a fixed depth), store children as separate rows linked by `k.id`, or store the tree as `k.json()` and check it with `.check(...)`.                                                  |
| `z.tuple([a, b])`                                                      | Use an object with named fields, or `k.array(k.union([a, b])).length(2)` with a `.check` on positions.                                                                                                                                               |
| `z.instanceof`                                                         | Use the closest structural schema plus `.refine(...)`, or `k.custom<T>(guard)`. Convex values cannot be class instances except `ArrayBuffer` (`k.bytes()`).                                                                                          |
| `z.undefined()`, `z.void()` outside `returns`                          | Make the field `.optional()`. In `returns`, use `k.void()`.                                                                                                                                                                                          |
| `z.enum(NumericEnum)`, `z.nativeEnum(NumericEnum)`                     | `k.enum` takes string values only. Use `k.union([k.literal(0), k.literal(1)])`, or switch the enum to string values.                                                                                                                                 |
| `z.coerce.*`, `z.preprocess`                                           | Use an input-position `.transform(...)` from the raw type, for example `k.string().regex(/^\d+$/).transform(Number)`.                                                                                                                                |
| `z.codec`                                                              | Use a `.transform` on input and convert on output in the handler.                                                                                                                                                                                    |
| `.brand()`, `.readonly()`                                              | Not supported. Use `k.id('table')` for ids; brand other types in app TypeScript.                                                                                                                                                                     |
| `.meta({...})`                                                         | Use `.describe(text)`.                                                                                                                                                                                                                               |
| Async refinements and transforms                                       | Move the work into the handler.                                                                                                                                                                                                                      |
| `.error` on a `safeParse` result, `._zod`, `.def`                      | Read `result.issues`; there are no Zod internals.                                                                                                                                                                                                    |
| String format helpers other than `email` and `url` (`uuid`, `ipv4`, …) | `k.string().regex(pattern, message)`.                                                                                                                                                                                                                |

App code that parses external data with Zod (JWT claims, webhook payloads, third-party API responses) is the app's own. It may keep importing `zod`; mark the file with the codemod keep marker. Keep such modules out of the import graph of Convex function modules where possible, because Zod in any imported module puts Zod back into that function's bundle.

### Schemas shared with Zod libraries

A workspace package often holds schemas that both Convex code and Zod libraries use: form resolvers and AI SDK tools. Write each such schema once, in `k`, in the shared package. Give each Zod consumer a converted copy at the point of use:

```ts
// packages/shared/src/invoice.ts
import { k } from 'cvx-kit/k'
export const invoiceInput = k.object({ number: k.string().trim().min(1), total: k.int().min(0) })

// apps/web/src/invoice-form.tsx: a library that takes Zod
import { zodResolver } from '@hookform/resolvers/zod'
import { toZod } from 'cvx-kit/zod/classic'
import { toZod as toMiniZod } from 'cvx-kit/zod'
import { invoiceInput } from '@acme/shared/invoice'
const resolver = zodResolver(toZod(invoiceInput)) // classic Zod
const tool = { inputSchema: toMiniZod(invoiceInput) } // zod/mini, for libraries that take any Zod 4 schema
```

The classic entry imports named constructors: the one-field bundle test measures 219,220 Zod bytes, including English error messages and zero non-English locale bytes, versus 79,065 bytes for Mini with no locales. Passing the whole namespace retains 771,692 Zod bytes in that test; a consumer measured 754 KB. The deprecated `toZod(schema, { zod: z })` option from `cvx-kit/zod` remains supported, but keeps all of Zod in the bundle.

Refinements, checks, normalisers, transforms and pipes are carried, so the Zod copy runs the same callbacks as the `k` schema; [Zod interop](#zod-interop) lists the three differences that remain. `.catch` is not carried. There is no conversion from Zod to `k`, which is why the `k` schema is the source. Keep `cvx-kit/zod` out of Convex function modules; it belongs where the Zod library is called.

The codemod follows this pattern. When a file passes a schema to a third-party library (a call whose callee chain starts at an import that is not `zod`, `cvx-kit`, `convex` or `convex-helpers`), it leaves that schema and everything it references in Zod and reports `zod-consumer`. When the schema comes from another file of the run, it rewrites the schema there and reports the consumer site as `zod-consumer-import`: use the schema directly for a Standard Schema consumer, or wrap the argument in `toZod(schema)` from `cvx-kit/zod/classic` for a library that needs classic Zod.

#### oRPC validation and OpenAPI

oRPC accepts `k` schemas directly because they implement Standard Schema. Pass the schema to `.input()` or `.output()` without converting it to Zod. For the OpenAPI document, register a converter that calls the kit's `toJsonSchema`:

```ts
import type { StandardSchemaV1 } from '@standard-schema/spec'
import { OpenAPIGenerator } from '@orpc/openapi'
import type { KSchema } from 'cvx-kit/k'
import { toJsonSchema } from 'cvx-kit/json-schema'

function isKSchema(schema: StandardSchemaV1 | undefined): schema is KSchema {
	return schema?.['~standard'].vendor === 'cvx-kit'
}

const generator = new OpenAPIGenerator({
	converters: [
		{
			condition: isKSchema,
			convert: (schema) => [isKSchema(schema) ? toJsonSchema(schema) : {}, false],
		},
	],
})
```

`KSchema` is a public type export, so the predicate uses the Standard Schema vendor rather than `instanceof`. This converter preserves the kit's patterns, numeric minimums, enum values and optional parameters in the OpenAPI document. `z.file()` has no `k` form: routes with file uploads keep Zod and its OpenAPI converter alongside this one. A consumer measured the cost of keeping both converters as +19 KB of kit and +7 KB of Zod in each bundle that imports the router.

### Files that keep Zod: use the namespace import

In a file that keeps Zod, import it as a namespace:

```ts
import * as z from 'zod' // not: import { z } from 'zod'
```

The named `{ z }` import keeps Zod's whole namespace object in the bundle, locale tables and JSON Schema converters included. Measured in the Accord trial of this release, not by the kit's own benchmarks: one service file bundled alone held 733 KB of Zod with `import { z }` and 194 KB with `import * as z`. One `import { z }` anywhere in a bundle, including in a dependency, keeps the whole namespace, which cost about 520 KB per function bundle there (737 KB against 213 KB). Check dependencies too: Accord's bundles stayed at 737 KB after its own files were changed, because one dependency still imports `{ z }`. The `import { z } from 'zod'` lines elsewhere in this guide show v1 code.

With `import * as z from 'zod/mini'`, no locale is loaded by default, so issues without a custom message read `Invalid input`. Call `z.config(z.locales.en())` once to enable English messages.

## The codemod

The codemod rewrites the mechanical majority of call sites and reports every site it left, by file, line and reason. It ships in the package as the `cvx-kit-codemod-v2` bin (source in `tools/codemod-v2/`), and its only dependency, `oxc-parser`, is a cvx-kit dependency. Install the 2.0 package first, then run it from the app's root, passing paths in your app. This guide also ships in the package, at `node_modules/cvx-kit/skills/cvx-kit/references/migration-v2.md`.

```sh
# 1. Dry run: writes nothing except the optional report
npx cvx-kit-codemod-v2 convex src --report codemod-report.json

# 2. Review the summary and the report, then write
npx cvx-kit-codemod-v2 convex src --write --report codemod-report.json
```

From a cvx-kit checkout, `node path/to/cvx-kit/tools/codemod-v2/index.mjs` is the same program.

Options: `--write` writes the files (without it nothing is written), `--report <file>` writes the JSON report, `--ext ts,tsx,mts` sets the extensions, `--no-getters` keeps function `args` and `returns` as data properties, `--native-number-bounds` omits the added `.finite()` on `k.number()` (see [Numbers](#numbers-accept-nan-and-infinity)), `--ignore <glob…>` skips paths, `--include-packages-without-kit` also rewrites packages that do not depend on cvx-kit, and `--help` prints the options. `node_modules`, `dist`, `build`, `.next`, `_generated`, `.git` and `.d.ts` files are always skipped. Run it on a clean working tree so the diff is reviewable. Running it twice changes nothing the second time. Pass every directory of the app in one run: the codemod reads all the files twice, so type helpers on imported schemas are judged with the whole run in view. `--no-strip-parsed` is accepted as a deprecated no-op and prints one line to stderr; it is omitted from help.

By default each file uses its nearest ancestor `package.json`, including one above the working directory. Packages must list `cvx-kit` in `dependencies`, `devDependencies`, `peerDependencies` or `optionalDependencies`, or be named `cvx-kit`. A package whose files import only client entries of the kit (`cvx-kit/react`, `cvx-kit/client`) is treated the same way, because its Zod (forms, API clients) does not reach Convex. Other packages are left `untouched`, with one informational `package-without-cvx-kit` entry per file and a unique `packagesWithoutKit` directory list in the report and summary. Pass `--include-packages-without-kit` to include them. Files with no manifest within that boundary are processed as before. This boundary does not apply to `--restore-strict`.

What it rewrites:

- `import { z } from 'zod'` → `import { k } from 'cvx-kit'`, dropping the Zod import when nothing uses it. A type-only import of the kit's `k` (`import type { k }`, `import { type k }`) is promoted to a value import, since the rewritten code uses `k` at runtime. A file that already imports `k` from `cvx-kit` or `cvx-kit/k` keeps that import, so a re-run after fixing reported sites picks up the rest.
- Number bounds: `z.int()`, `z.number().int()` and `z.number().safe()` → `k.int()`. Integer options stay on `.int(options)`. Redundant Zod `.safe()` calls on integer schemas are removed. `.int()` on aliases stays `.int()`; `.safe()` on proven numeric aliases becomes `.int()` unless the alias is already an integer. `z.number()` → `k.number().finite()`, unless `--native-number-bounds` is passed. Already-migrated `k` `.safe()` calls are left alone.
- Factories (`z.object` → `k.object`, `z.strictObject` → `k.strictObject`, `z.bigint` → `k.int64`, `z.partialRecord` with an enum, string literal or union of literals key → `k.partialRecord` and with a `z.string()` key → `k.record` (in Zod that is a plain record), `z.unknown` → `k.any`, `z.iso.date` → `k.isoDate`, `z.iso.datetime` → `k.isoDateTime`, and the rest by name).
- Bigint bounds: `z.bigint()` → `k.int64()` with bigint `.min`/`.max` and `.positive`/`.nonnegative`/`.negative`/`.nonpositive` checks and their message options. `.gte`/`.lte` become `.min`/`.max`; `.gt(0n)`/`.lt(0n)` become `.positive()`/`.negative()`. Nonzero exclusive bounds and `.multipleOf` stay Zod with `unknown-method`. The same inclusive aliases and zero-exclusive aliases work on numbers.
- Chains: `.nullish()` → `.nullable().optional()`, `.nonempty()` → `.min(1)`, `.normalize(form)` → `.overwrite(value => value.normalize(form))`, `.strict()` kept, `.pick({ a: true })`/`.omit({ a: true })`/`.partial({ a: true })`/`.required({ a: true })` → string keys. `.positive()`, `.negative()`, `.nonnegative()`, `.nonpositive()`, `.finite()`, `.required()`, `.keyof()`, `.exclude()`, `.extract()`, `.removeDefault()` and a `k`-form `.check((value, ctx) => …)` are kept as written.
- The same chain rewrites on a chain that starts at a schema the codemod can see is `k` (declared with `k.` in the file, or rewritten in this run) or at a table boundary member (`ledger.storage.pick({ amount: true })` → `.pick('amount')`), including tables already declared with `kTable` and tables imported from another file of the run.
- Factories whose arguments decide the mapping: `z.iso.datetime({ offset: true })` → `k.isoDateTime()`; `z.instanceof(ArrayBuffer)` → `k.bytes()` (reported as `bytes-validator-narrowed`); `z.void()` as the value of `returns` → `k.void()`; `z.enum` with one argument that is an array, an object literal of strings, a `const` object of strings or a TypeScript string enum → `k.enum`; a `z.enum` with a second (options) argument is held and reported.
- `zodToConvex(schema)` → `schema.validator` when the argument is a schema the codemod can prove.
- `zid('t')` → `k.id('t')`. When a statement held as Zod still calls a `zid` imported from `cvx-kit/zod-table`, the import moves to `convex-helpers/server/zod4`, so the file compiles, and each such reference is reported as `zid-in-zod-statement`. The table callback form `(id) => ({ … })` → a plain object, for `zodTable`, `createTable(...)`, `tenantTable` and `zodVariantTable`. An identifier or member reference to a field object is accepted directly; only an actual callback that cannot be unwrapped gets `table-callback-complex`.
- `zodTable` → `kTable`, `zodVariantTable` → `kVariantTable`, `zodContract` → `kContract`, `effectZodApiBuilder` → `effectApiBuilder`, and `cvx-kit/zod-table` imports → `cvx-kit/table`. convex-helpers' `zCustomQuery`, `zCustomMutation`, `zCustomAction` (from `convex-helpers/server/zod4`) → `kCustomQuery`, `kCustomMutation`, `kCustomAction`, and `ZCustomCtx` → `KCustomCtx`, imported from `cvx-kit/registration`. These kit imports and names are rewritten in every file, including files with no Zod, because the v1 entries do not exist in v2. A statement held as Zod is the exception: it keeps its v1 names and the imports it needs, and is reported, so it must be migrated by hand before the file compiles against v2. A moved name joins an existing import of its new module instead of adding a second one.
- `z.infer`, `z.input`, `z.output` → `k.infer`, `k.input`, `k.output` when the type argument is `typeof` a schema that is `k` after the run: declared in the file, or imported from a file of the run that exports it as `k`. Known derivations include `.extend`, `.pick`, `.omit`, `.partial`, `.required`, `.optional`, `.nullable`, `.strict`, `.strip`, and table `.insertSchema`, `.updateSchema`, `.commandInput`, `.publicDto`, `.schema`, `.doc`. Local bindings that shadow a Zod import are ignored; type-only Zod imports still support these helpers. Otherwise the helper stays Zod and is reported as `type-helper-unknown`, because `k.infer` of a Zod schema is silently `unknown`.
- Function definitions (an object literal passed to a call and carrying a `handler`): `args: <expr>` and `returns: <expr>` become `get args() { return <expr> }` and `get returns() { return <expr> }`, unless the value is a plain reference (`NoteArgs`, `schemas.byId`) or mentions `this`, `await` or `yield`. Convex re-evaluates a module's import graph on every call, so a getter makes a call build only the validators of the function it serves; on the benchmark app (about 30 tables, 14 functions) module load went from 8.43 ms to 6.30 ms. The getters are written on one line; run your formatter afterwards. Pass `--no-getters` to keep data properties, which stay supported.

Within a file, statements whose schemas reference each other move together: if one of them has an unsupported site, the whole group stays Zod byte for byte and the others are reported as `mixed-reference`. A held statement keeps its v1 form, including a `zodTable` call. Each file gets a status: `rewritten`, `mixed` (some Zod or v1 kit names remain), `kept`, `untouched` or `error` (the file did not parse). `kept` means the file holds at least one Zod declaration the codemod left on purpose and listed in the report (under the keep marker as `keep-zod-marker`, or with the reason it was held). A file whose only Zod is type references to schemas outside the run is not `kept`. The run exits 1 when any file is `error` or any site is `held-pipe-to-k` (after writing the report) and 0 otherwise; other skipped sites do not fail it. Paths must be files or directories: the codemod does not expand globs, so a quoted glob fails with a message saying so.

Add the keep marker as a comment anywhere in a file the codemod must leave alone, such as a module that parses external data with Zod. A reason may follow it:

```ts
// cvx-kit-codemod: keep-zod -- the provider SDK validates with Zod
```

A no-op re-run keeps a file with remaining Zod declarations `mixed` when it also uses `k`, or `kept` when it is Zod-only. It counts the declarations left as Zod, but counts only declarations edited in this run as rewritten; existing `k` declarations do not inflate that count.

The report holds `packagesWithoutKit` (skipped package directories), `summary` (file counts by status), `outsideRoots` (symlinks whose real path is outside the given paths, which are skipped so `--write` never edits a file outside them), `declarations` (rewritten and left), `mechanicalShare`, `totals` and `info` (counts by reason code), and `files` with every skipped site's `line`, `column`, `code` and `text`.

| Reason code                  | Meaning                                                                                                                                                                                                                                       | What to do                                                                                                                                      |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `loose-object`               | `.catchall()` (`z.looseObject` and `.passthrough()` are rewritten to `k.looseObject` and `.loose()`)                                                                                                                                          | Decide per site; see [No v2 form](#constructs-with-no-v2-form).                                                                                 |
| `catch`                      | `.catch(...)` whose callback reads Zod's `ctx.value` or `ctx.error`, or has no single argument                                                                                                                                                | Read `input` and `issues` instead; `k` passes `{ issues, input }`.                                                                              |

### Object policies in the codemod

`z.object` becomes `k.object` without adding `.strip()`: both strip unknown keys during application parse. `z.strictObject` becomes `k.strictObject`, and source `.strict()` and `.strip()` calls are kept. `.loose()` and `.passthrough()` retain their existing rewrites. Derived objects keep the receiver's policy, so no parse-use classification or object-strictness report codes are needed. Kit boundaries still reject unknown keys.

The deprecated `--no-strip-parsed` flag has no effect on output. Re-running the codemod leaves existing `.strip()` and `.safe()` calls in already-migrated `k` code unchanged.

The informational `check-options-by-reference` marks a check whose options object is passed by reference (`refine(fn, options)`): the codemod rewrites an inline `error: '…'` to `message: '…'` but cannot see inside a reference. `k` accepts `error` as a string alias of `message`, so such options keep working; a function-valued `error` throws at declaration.

The informational `table-spread` marks a spread of a table boundary (`{ ...table, table: other }`). It works in 2.0 (see [Replacing a member](table.md#replacing-a-member)) and builds every boundary of that table at the spread.

Limits:

- Across files the codemod knows only the files of the run. It resolves imports between them through relative paths, `tsconfig` path aliases and workspace packages (`workspaces` in `package.json` or `pnpm-workspace.yaml`) when it learns which imports are tables or `k` schemas. A rewritten module that uses a schema from a file outside the run is judged as unknown: its type helpers are reported, and a value use is left for the typecheck.
- `insert({ a: true })` and `update({ a: true })` call sites on table boundaries are not rewritten or reported; the typecheck finds them. Change them to `insert('a')`.
- It does not change behaviour that the code depends on: return stripping, `ZodError` readers, async refinements and branded ids on input are yours to fix.

## Migration order

1. Create one branch for the whole Convex project. v1 is removed from the package, so v1 and v2 kit tables cannot coexist in one install; the project switches together.
2. Record the current pushed schema (see the checklist below) before changing code.
3. Upgrade cvx-kit and the peers, then run the codemod in dry-run mode and read the report.
4. Run it with `--write`, then fix the reported sites and the type errors, starting from leaf modules of the import graph: shared constants and field schemas first, then table modules, then contracts and registries, then function modules. A module's errors often come from a schema it imports, so fixing leaves first avoids chasing the same error in many files.
5. Fix the behaviour changes: returns that relied on stripping, derived objects of refined objects, `ZodError` readers, ids typed as `string`, async refinements.
6. Verify, then deploy.

A function module gets faster only once its whole import graph is Zod-free. One module that still imports `zod` (an app helper, a shared schema, `cvx-kit/zod`) puts Zod into the bundle of every function module that imports it. Find those modules with the bundle check below and move Zod-using code out of shared schema files.

No data migration is expected: the stored shape and indexes are unchanged. If `npx convex dev` or `npx convex deploy` reports a schema validation error against existing documents, the pushed schema changed. Compare the schema before and after (below) and look for:

- a field that became required, for example a default removed or `.optional()` dropped;
- an enum or literal union that lost a value;
- a field whose type changed, for example `z.date()` or a transform replaced by a different stored type;
- a table whose fields moved under `createTable` shared fields with a different definition;
- `z.looseObject` data (now `k.looseObject`, same closed native object): if documents were written with extra keys through a native path, a strict object rejects them. Declare the keys or use a `k.record` field.

## Verification checklist

- [ ] `tsc --noEmit` (or the app's typecheck) passes.
- [ ] The app's tests pass, including DTO redaction, denied access, wrong-table ids, invalid patches and rollback.
- [ ] The pushed schema is unchanged. Print it before and after and diff the output:

  ```ts
  // scripts/print-schema.ts — run with bun or tsx before and after the migration
  import schema from '../convex/schema'

  // export() is what Convex pushes; it is internal in the Convex types.
  const exported = (schema as unknown as { export(): string }).export()
  console.log(JSON.stringify(JSON.parse(exported), null, 2))
  ```

- [ ] `npx convex dev --once` pushes without schema validation errors, against a local deployment if you have one. convex-test does not check exported validators the way the backend does (it accepts a record with literal keys, for example) and always loads the schema, so it hides an index declared in a module a function does not import. Only a push catches those; see [Declare indexes in the table's own module](table.md#declare-indexes-in-the-tables-own-module).
- [ ] The function validators are unchanged, or changed only where you meant them to. Print the function spec before and after and diff it:

  ```sh
  npx convex function-spec > /tmp/spec-before.json   # with the pre-migration code pushed
  npx convex function-spec > /tmp/spec-after.json    # with the migrated code pushed
  diff /tmp/spec-before.json /tmp/spec-after.json
  ```

  This catches validator changes that the schema diff cannot see, such as `z.instanceof(ArrayBuffer)` exporting `v.any()` in v1 and `k.bytes()` exporting `v.bytes()`. It covers the root app's functions only, not component functions; check those through the schema and the tests.

- [ ] No function bundle contains Zod. Bundle a function module the way Convex does and list Zod inputs:

  ```sh
  npx esbuild convex/documents.ts --bundle --platform=browser --format=esm \
    --conditions=convex,module --external:node:* --metafile=/tmp/meta.json --outfile=/tmp/out.mjs
  node -e "const m=require('/tmp/meta.json');console.log(Object.keys(m.inputs).filter((p)=>/node_modules\/(zod|convex-helpers\/server\/zod)/.test(p)))"
  ```

  An empty list means the module loads no Zod. Repeat for each function module, or for a module that re-exports them all.

- [ ] `grep -rn "from 'zod'" convex` lists only files that are meant to keep Zod (marked with the keep marker), and each uses `import * as z from 'zod'`.
- [ ] Clients read `error.data.code === 'VALIDATION'` instead of `ZodError`.

## Client-side changes

- Validation failures arrive as `ConvexError` with `data: { code: 'VALIDATION', issues: [{ path, code, message }] }`. Structural failures raised by Convex keep Convex's own error. An error contract decodes only the codes it declares, so read `error.data` directly for validation failures. See [client-failures](client-failures.md).
- Forms: `k` schemas implement Standard Schema v1, so form libraries that accept Standard Schema (for example TanStack Form) take them directly, including `documents.commandInput`. Libraries that need Zod can use `toZod(schema)` from `cvx-kit/zod`, or `toZod(schema)` from `cvx-kit/zod/classic` for classic Zod; refinements and transforms are carried. See [Schemas shared with Zod libraries](#schemas-shared-with-zod-libraries).
- Frontend Zod schemas that are not shared with Convex code do not need to change.
- Ids typed `Id<'table'>` on input: pass ids from query results or the generated data model, not plain strings.

## Measured results

The benchmark record is `docs/benchmarks/validators.md` in the repository. On one consumer app's finance-contract schema graph (350 schemas), declaring the schemas on import fell from 23.44 ms with classic Zod to 4.78 ms with `k` (79.6% lower), and retained heap from 10.56 MB to 1.61 MB. On the representative benchmark app a function module's bundle fell from 815.8 KB to 220.6 KB and its load time from 28.34 ms to 7.97 ms.
